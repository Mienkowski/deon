# CLAUDE.md

Guidance for AI assistants (and humans) working in this repository.

## What this project is

`deon` is a command-line tool that adds an **ethics checklist** to data science
projects. It renders a checklist (default: `deon/assets/checklist.yml`) into one
of several file formats, either printing to stdout or writing/appending to an
output file. It is published to [PyPI](https://pypi.org/project/deon/) and
conda-forge, and is maintained by [DrivenData](https://www.drivendata.org/).

- Project homepage / docs: http://deon.drivendata.org/
- Upstream repo: https://github.com/drivendataorg/deon
- Current version: see `VERSION` (single source of truth, currently `0.3.0`)
- Python: requires **Python >=3.6** to run the tool (CI tests 3.6, 3.7, 3.8).

## Repository layout

```
deon/                       # the Python package
  cli.py                    # Click CLI entry point (`deon` command -> main())
  deon.py                   # create() orchestrator + custom exceptions
  parser.py                 # Checklist/Section/Line data model, reads YAML
  formats.py                # Format classes + FORMATS/EXTENSIONS registries
  __init__.py               # exposes create(), ExtensionException, FormatException
  __main__.py               # enables `python -m deon`
  assets/
    checklist.yml           # DEFAULT checklist (English) -- source of truth for items
    checklist_pt-BR.yml     # Portuguese (Brazil) translation
    examples_of_ethical_issues.yml       # real-world harm examples per line_id
    examples_of_ethical_issues_pt-BR.yml # pt-BR translation
tests/                      # pytest suite (see Testing)
docs/                       # mkdocs site + template rendering (see Docs)
  md_templates/             # jinja2 templates for README.md and docs pages
  render_templates.py       # renders templates -> README.md, docs/docs/*.md
  mkdocs.yml
examples/                   # GENERATED example output (ethics.md/.ipynb/.html/.rst/.txt)
README.md                   # GENERATED from docs/md_templates/readme.tpl -- do not edit directly
Makefile                    # dev workflow entry points
VERSION                     # version string; bumping it on master triggers a release
```

## How the code works

The rendering pipeline is small and worth understanding before making changes:

1. **`cli.py`** defines the `deon` Click command and its options
   (`--checklist/-l`, `--format/-f`, `--output/-o`, `--overwrite/-w`,
   `--multicell/-m`). It calls `create()` and translates the custom exceptions
   into user-facing `click.ClickException` help messages.
2. **`deon.py::create()`** loads the checklist YAML into a `Checklist`, decides
   the output format (file extension wins over `--format`, default `markdown`),
   handles the `--multicell` special case (jupyter only), then instantiates the
   right `Format` subclass and either `.render()`s to stdout or `.write()`s to a
   file.
3. **`parser.py`** holds the plain data model: `Checklist` -> `Section`s ->
   `Line`s, with `Checklist.read(path)` parsing a YAML file via
   `yaml.SafeLoader`.
4. **`formats.py`** is where each output format lives. The base `Format` class
   renders via string templates (`template`, `section_template`,
   `line_template`, plus delimiters). Subclasses (`Markdown`, `Rst`, `Html`,
   `JupyterNotebook`, `JupyterNotebookMulticell`) override templates or, for
   non-text formats, override `render()`/`write()`. Two registries at the bottom
   map names and extensions:
   - `FORMATS`: format name -> `Format` subclass
   - `EXTENSIONS`: file extension -> format name

Notable behavior: when an output file already exists and `--overwrite` is not
set, the checklist is **appended** (markdown/rst/txt via `append_delimiter`;
jupyter by adding cells; html by extending `<body>`).

### Adding a new output format

Add a `Format` subclass in `formats.py`, then register it in **both** `FORMATS`
(by name) and `EXTENSIONS` (by extension). Add a `known_good_*` fixture in
`tests/assets.py`, wire it into `tests/conftest.py::test_format_configs`, and
the parametrized tests will cover it. The README/docs list of supported formats
is generated from `EXTENSIONS`, so re-render docs (below).

## The checklist is generated content — this matters

Several files in this repo are **generated** and must not be hand-edited. The
source of truth is `deon/assets/*.yml`, and the render step produces the rest:

- `README.md` — generated from `docs/md_templates/readme.tpl`
- `docs/docs/index.md`, `docs/docs/examples.md` — generated from templates
- `examples/ethics.{md,ipynb,html,rst,txt}` — generated by running the CLI

The pre-commit hook (`.precommithook`, installed via `make register_hook`) runs
`make build` and **fails the commit** if generating content produced changes you
didn't stage. In practice: after changing a checklist item, CLI options, or
anything surfaced in docs/examples, you must re-render and commit the generated
output too.

To regenerate everything:

```
make examples      # regenerate examples/ethics.* from the current checklist
make docs          # render templates (README + docs) and build the mkdocs site
# or just the markdown render step:
cd docs && python render_templates.py
```

### Changing checklist items

Per project policy (see README "Changing the checklist"), item changes go
through an issue process. A PR that adds/changes an item must update **both**:

- `deon/assets/checklist.yml` (the item)
- `deon/assets/examples_of_ethical_issues.yml` (a real-world harm example for
  that `line_id`)

Keep `line_id`s consistent between the two files — `render_templates.py` joins
them by `line_id` to build the examples table. If you touch the English YAML,
consider whether the `pt-BR` counterparts need updating too.

Checklist YAML schema (also enforced implicitly by `parser.py`):

```yaml
title: TITLE
sections:
  - title: SECTION TITLE
    section_id: A            # short id, becomes the section prefix
    lines:
      - line_id: A.1         # unique id, used to join with examples
        line_summary: 1-3 word shorthand
        line: Full question text.
```

## Development workflow

Setup (installs deps in editable mode and registers the pre-commit hook):

```
make reqs          # pip install -r dev-requirements.txt (+ registers hook)
```

Common commands (all defined in the `Makefile`):

| Command | What it does |
| --- | --- |
| `make test` | Runs `make lint` then `pytest -vv` (with coverage) |
| `make lint` | `black --check deon tests docs` and `flake8 .` |
| `make format` | Auto-format with `black` |
| `make examples` | Regenerate `examples/ethics.*` via the CLI |
| `make docs` | Render templates and `mkdocs build` |
| `make build` | `test` + `examples` + `docs` (what pre-commit runs) |
| `make register_hook` | Install the git pre-commit hook |
| `make package` | Build sdist (runs build + clean first) |

### Style / linting

- **Formatter:** `black`, line length **99** (`pyproject.toml`), targets
  py36/py37/py38.
- **Linter:** `flake8`, max line length 99, ignoring `E501` and `W503`
  (`setup.cfg`).
- Run `make format` before committing; `make lint` is part of `make test` and CI
  will fail on unformatted code or lint errors.

## Testing

- Framework: **pytest**, config in `pytest.ini` (testpaths=`tests`) and
  `setup.cfg`. Coverage is on by default (`--cov`), producing term/html/xml
  reports; `coverage.xml` is uploaded to codecov in CI.
- Run: `pytest -vv` or `make test`.
- Key files:
  - `tests/conftest.py` — fixtures: a temp `checklist` YAML, and
    `test_format_configs` (the (format, filename, known-good) matrix).
  - `tests/assets.py` — the `known_good_*` expected rendered outputs for each
    format. **When output rendering changes, update these fixtures.**
  - `tests/test_deon.py` — render/write/overwrite/multicell behavior.
  - `tests/test_cli.py` — Click CLI behavior, error messages, and a subprocess
    smoke test of `deon` and `python -m deon` across all formats.
  - `tests/test_formats.py`, `tests/test_parser.py` — unit-level coverage.

## Docs

- Docs are built with **mkdocs** (alabaster theme) from `docs/`.
- `docs/render_templates.py` uses **jinja2** to render `md_templates/*.tpl`
  into `README.md` and `docs/docs/*.md`. It injects the live rendered default
  checklist, the CLI `--help` output, the supported-formats map, and the
  examples-links table — so docs stay in sync with the code automatically.
- Because README/docs are generated, **edit the `.tpl` templates in
  `docs/md_templates/`, not the output files.**

## CI / Release

- **`.github/workflows/tests.yml`** — runs on push to `master`, on PRs, and
  weekly. Matrix over {ubuntu, macos, windows} x Python {3.6, 3.7, 3.8}. Runs
  `make test`, uploads coverage (ubuntu/3.8 only), then `make examples` +
  `make docs` to verify doc/example generation.
- **`.github/workflows/release.yml`** — triggers on pushes to `master` that
  change `VERSION`. Builds the package, publishes to Test PyPI then Production
  PyPI, tags the commit `v<VERSION>`, and creates a GitHub release. Guarded to
  the `drivendataorg/deon` repo.
- **Releasing** (maintainers): bump `VERSION` and merge to `master`; the release
  workflow does the rest (see `CONTRIBUTING.md`).

## Conventions & gotchas for changes

- **Never hand-edit generated files** (`README.md`, `examples/ethics.*`,
  `docs/docs/index.md`, `docs/docs/examples.md`). Change the source
  (`deon/assets/*.yml` or `docs/md_templates/*.tpl`) and re-render with
  `make build` / `make docs` / `make examples`.
- After any change that affects rendered output, **run `make build`** so the
  pre-commit hook won't reject your commit for unstaged generated changes.
- Keep `black`/`flake8` clean at line-length 99.
- When adding a format, register it in both `FORMATS` and `EXTENSIONS` and add
  `known_good_*` test fixtures.
- The `ETHICS_CHECKLIST` env var can override the default checklist path
  (`deon/deon.py`), independent of the `-l/--checklist` flag.
- Package data (checklists) is shipped via `MANIFEST.in` + `include_package_data`
  — new asset files must be added to `MANIFEST.in` to be packaged.
